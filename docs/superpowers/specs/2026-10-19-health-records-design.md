# StrideHub 数据记录与展示重构

用户要求把产品重心从 Dreeve 配置后台转回个人数据的保存和展示，统一原有及新增页面；让 AI 通过详细观测制定课表、减重与生活计划，页面负责展示与执行反馈。

## 已选择的界面方向

沿用现有 Symfony/Twig 与浏览器脚本，避免另建一套应用造成第三套体验。所有日常页面共用四个入口：总览、身体、运动、计划。文件导入、设置、原运动详情也使用相同外壳；根路径和登录进入受保护总览。高级配置放在次级入口。

视觉由浅灰蓝 #f2f5f9、墨蓝 #132b46、钴蓝 #4666ed、睡眠紫 #8a75e5、薄荷 #37b4a0、温橙 #e7a456 构成。系统字体优先 Avenir Next / PingFang SC。睡眠主卡采用月相 SVG 与阶段色条作为主要视觉记忆，其余区域以安静的白色记录面板承载数据；图标使用同一线条风格。手机保留四主入口，不横向溢出，减少配置表单占用。

总览：最近实际睡眠、阶段累计时长、带缺口的趋势、最近活动与身体信号、运动、下一份已保存计划、数据来源/同步状态。所有最近数据都有日期，不把最近记录称为今天。阶段构成不冒充整夜发生顺序；不推算恢复分、医疗结论或未返回的传感器值。

身体：睡眠摘要/趋势与可展开历史、直接记录体重、逐日设备明细和分钟心率、血压。体重沿用原 Setting 唯一数据源，输入固定 kg 并适配旧单位。刷新保留草稿；保存时锁定输入，版本冲突必须读取核对，保存成功后再读回验证。

运动：优先展示直接同步的 Zepp 云端记录及传感器曲线。已有文件导入跑步分析保留相同外壳，但统计不叠加，避免重复计数。原始源内容供 AI 按需读取，列表仅轻量摘要。

计划：训练课表与减重/作息/饮食/恢复计划共处一个入口。显示目标、来源、AI 理由、日期、条目和状态。用户能标记条目完成；AI 使用已有认证 API 保存新计划或带版本更新，不在浏览器存储 API 密钥。未指定日期不等于每日重复。界面不假称已经连接 AI 或自动生成计划。

## 数据要求

Zepp 日数据分标准化汇总、按需采样、原始来源留存。原始字段不能只提取睡眠后丢弃。无记录是 null/缺口，不是 0。部分接口失败不删除已有来源；新响应缺测量时保留旧已知信息，并标注保留字段。所有入口绑定同一账号归属，避免账号变更混入历史；采用数据库版本栅栏及本地锁。

新增健康计划复用 TrainingRecord 的版本与并发保护。详细日记录、原始数据、运动源记录都使用现有 Bearer 或管理员会话鉴权，网页写入要求 CSRF，禁止健康响应缓存。真实凭据与个人数据保存在 Git 忽略的私有路径。

## 验收边界

实际 Zepp 读取要区分云端拒绝、缺数据和成功，不能用 fixture 数量充当用户数据。浏览器写入测试使用独立 8084/DEMO 数据库；个人 8081 数据库仅做授权同步和只读展示验证。检查总览、日期切换、窄屏、体重保存与草稿/冲突、计划下发/完成、同步错误、旧详情与上传。发布和目标 NAS 部署是独立步骤，本轮不假称已部署远端。
