# StrideHub 全原生 Android 客户端设计

状态：用户于 2026-10-23 确认按本方案直接实施。实施与验证进度见对应计划和验收记录。

## 用户要求与验收原则

用户确认：App 内全部使用原生 Android，不能有 WebView。这取代 2026-09-29 Android 方案中“原生外壳承载管理网页”的选择。

零 WebView 覆盖主页面、登录、详情、图表、表单、导入、设置、称重配对及错误处理；不得用隐藏 WebView、网页表单脚本、内嵌浏览器或网页图表作为实现捷径。App 提供的功能必须能够在原生界面完成，不以“在浏览器中打开管理网页”补齐尚未完成的功能。

范围按现有 App 的业务入口核对：总览、身体、运动、计划、称重，以及更多菜单中的饮食、减重目标、今日安排与反馈、文件导入、运动记录管理、连接切换和退出。沿这些业务入口使用的查看、创建、编辑、删除、筛选、同步和错误恢复也纳入。外部资料链接可以交给系统默认浏览器，但不承载 App 内部业务。

“全部原生”是已确认的技术边界；尚未把网页版所有服务器运维功能复制到手机列为用户已确认的需求。本文提议保留手机现有业务能力并完成原生化；容器管理、服务器文件路径配置等无现有手机专用流程的运维能力不主动扩张到 App。

## 现状与原因

- `android/app/src/main/java/io/stridehub/app/BrowserLayout.java:66` 创建单个 WebView。
- `NavigationSection.java:7-9` 把四个主要栏目映射到 `/admin/...`；`MainActivity.java:131-156` 点击后加载网页，只有称重启动原生 Activity。
- 连接表单本身原生，但 `MainActivity.java:203-215` 仍通过网页及 JavaScript 提交登录。
- 返回按网页历史执行，栏目没有独立返回栈；进程重建重新进入总览；主要业务没有本地数据缓存。
- 蓝牙协议、稳定读数识别、身体成分计算、称重 SQLite 历史、CSV 导入和持久上传队列已经原生实现，可保留。
- 后端已有健康工作台、统一运动、训练、健康计划、饮食和身体记录 JSON API，业务规则无需移植到客户端重复实现。

## 方案选择

1. 保留网页，继续改外壳或网页样式：与用户零 WebView 要求冲突，排除。
2. 全原生界面，继续 Java 和手工 Android View：技术上符合要求，但当前仅连接和称重页面可直接复用，仍需建立新的导航、状态和数据层。
3. 全原生界面，Kotlin + Jetpack Compose + Material 3；复用稳定的 Java 业务代码和后端 API：本文推荐。新页面共享导航、主题、无障碍和生命周期状态管理，现有 BLE 与算法无需先翻译成 Kotlin。

用户已选择全原生边界；Compose、下面的导航安排和缓存策略是实现建议，不表述为用户已经逐项批准。

## 原生产品体验

保留“总览、身体、运动、计划”四个主栏目。称重作为全局快捷动作和身体页入口，保留桌面称重快捷方式以及未登录时的离线入口。各栏目独立保存详情路径、筛选与滚动位置。称重、趋势、历史、设备设置进入同一导航体系，不再打开另一套带重复主导航的小应用。

| 页面/流程 | 原生功能与完成标准 |
| --- | --- |
| 连接与账号 | 服务器地址、用户名、密码、保持登录、明确允许局域网 HTTP；原生提交和错误提示；切换账号/服务器和退出。旧后端缺少移动接口时明确提示需要升级，不回退网页。 |
| 总览 | 最近真实记录的日期、睡眠、身体指标、近期运动、下一项计划、同步状态；下拉刷新局部更新，缓存内容继续可见。 |
| 身体 | 睡眠摘要与历史、日指标、分钟心率、血压、身体测量和体重趋势；原生日期选择、详情和录入。缺失值保留缺口，不绘制成零。 |
| 运动 | Zepp 与文件导入的统一列表、类型/日期筛选、分页、详情、配速/心率等曲线、分段与计圈、轨迹和来源、重复记录确认与关联；保留已有跑步分析。 |
| 计划 | 训练课表及健康/饮食/作息/减重等已保存计划、详情、条目完成、今日安排、训练关联、执行反馈与比较；支持现有计划编辑能力。AI 来源与理由如实展示，不虚构自动规划服务。 |
| 称重 | 自动寻找已记住的体脂秤、实时值与已保存值区分、稳定测量确认、手动补录、历史、趋势、个人资料、设备切换、CSV 导入导出、同步与备份状态。 |
| 常用记录 | 饮食记录、饮食计划、减重目标、健康背景、身体记录和训练反馈的原生查看与增删改；字段校验、保存状态、版本冲突和草稿保留。 |
| 文件与运动管理 | 系统文件选择器、上传进度和真实导入结果、失败重试、原始运动记录查看与现有新增/编辑/删除流程、GPX 等导出。 |
| 设置与同步 | 当前服务器和账号、连接状态、Zepp 同步状态与触发、称重绑定/队列、设备权限、主题与常见错误恢复；业务操作不链接到管理网页。 |

界面沿用现有 StrideHub 的蓝色、睡眠紫和柔和背景作为品牌基础，使用原生导航栏、日期/时间选择器、底部面板、列表、键盘和返回手势。支持深色模式、系统字体大小、TalkBack 和系统边到边布局。图表采用原生绘制；轨迹使用原生绘制或经核实无 WebView 的地图组件，缺底图时仍可显示轨迹及指标。不能把 HTML 图表塞进“原生图表”组件。

## 客户端结构与数据

- 单一原生主 Activity，Compose 页面与有状态导航；ViewModel 管理屏幕状态，协程执行网络和数据库操作。进程重建恢复路径与必要草稿，不保存密码。
- 统一 API 客户端和 Repository；页面不直接解析网页。集中处理认证过期、连接失败、字段错误、版本冲突、取消、重试与服务端版本兼容。
- 新的本地缓存使用 Room，按规范化服务器地址与账号身份隔离。与现有称重数据库分开，避免为了界面改造重建已有称重表。
- 总览、身体、运动列表/已访问详情和计划支持读取上次成功缓存，明确数据时间和“离线/待刷新”。响应继续使用服务端 no-store，缓存由 App 显式管理，不启用代理或通用 HTTP 健康数据缓存。
- 第一版离线写入支持已有称重队列和表单草稿。训练、饮食、计划等修改需要在线确认；网络中断不伪称已保存，不对所有操作盲目自动重放。409 保留本地草稿并展示最新服务器版本供核对。
- 登出/切换清理当前账号的会话和业务缓存；本机称重历史保留，原目的地上传队列暂停。禁止把旧账号草稿、缓存或待上传记录交给新账号。
- 本地健康数据位于应用私有空间，继续禁用系统备份和应用数据迁移；设备凭据由 Android Keystore 保护，日志不包含口令、token、完整健康载荷。

## 原生认证与称重绑定

现有 `/api/v1` 接受服务器全局 API token；现有 `shdevice_` 凭据只适用于称重 `/device/v1`。不得把全局 API key 打包到 APK 或要求用户复制它，也不得把称重 token 悄悄扩大为通用凭据。

新增 JSON 移动会话接口，使用现有管理员用户名与密码校验，无 HTML、DOM 或 CookieManager 依赖。建议 `/mobile/v1/sessions` 创建会话、`/mobile/v1/session` 查询及撤销当前会话；具体命名可由实现者依仓库约定调整。

- 服务端发放随机、高熵、可撤销的设备会话 token，只存散列；绑定当前管理员身份、凭据版本、设备和过期时间。身份或管理员密码变更后旧会话失效。
- 会话最长七天，与现有保持登录期限一致；勾选保持登录才加密持久化。未勾选时只在进程内持有。到期重新输入密码；第一版不增加复杂刷新 token 协议。
- 在已有 JSON API 鉴权层识别移动会话，并限制于 App 所需的健康、训练、运动、档案、导入和移动设备操作；不给它 MCP 或任意管理路由权限。原有全局 API 和网页会话继续兼容。
- 登录具有失败限流和统一错误信息；沿用服务器子目录、同源凭据边界和有效证书验证。局域网 HTTP 必须保留明确用户选择。
- 退出立即清除本机凭据并暂停同步；在线时撤销服务端会话，离线时如实告知本机已退出、服务端凭据仍受有效期限制。
- 提供原生称重配对 API，复用既有设备注册/令牌轮换逻辑。只在用户选择同步时绑定，不因登录自动上传全部历史。
- 同一服务器和账号沿用现有 deviceId、measurementId、冻结载荷和队列收据语义；现有有效称重凭据可以继续使用。新配对只恢复原目的地可恢复队列，不能复活冲突/删除记录或重复生成已上传记录。

## 后端复用和补齐

| 能力 | 已有接口/服务 | 需要补齐 |
| --- | --- | --- |
| 首页/身体 | `GET /api/v1/health/workspace`，HealthWorkspace | 移动会话授权、能力/版本说明；默认日期窗口控制响应大小。 |
| 运动 | `/api/v1/health/workouts`、`/activities/{id}`、`/running/activities/{id}`、`/health/zepp/workouts/{id}` | 统一运动列表稳定分页；详情按来源分派，保留来源别名，不在客户端重新盲目去重。 |
| 健康/计划/训练录入 | `/api/v1/health/...` 与 `/api/v1/training/...` | 保留已有 version、409、428 和删除语义；补手机必需但目前仅网页拥有的操作。 |
| 文件与运动管理 | `/api/v1/activity/upload`、现有运动领域命令 | 上传回执补 importId，提供单文件处理状态/错误/重试；为当前通过网页及 Cookie 命令接口完成的新增/编辑/删除/enrich 补专用 JSON 接口，复用领域校验。 |
| Zepp 同步 | daily/workouts/sleep 的 status 与 sync | 原生展示持久任务状态；长请求改成可查询的异步任务，返回任务 ID，按已有账号锁避免重复运行，服务重启后正确恢复/标记中断。 |
| 称重 | LocalStore、NasSync、SyncJob、后端 collection | 移除 Cookie 依赖的配对入口，保持已有绑定、队列、幂等和删除保护。 |

Zepp 部分现有请求允许执行 660 秒，不能直接使用称重客户端 15 秒超时。新增的同步任务由后端承担，App 查询任务状态；手机退到后台不取消已提交的任务，也不以请求超时判定任务失败后重复发起。失联时显示最后已知状态，恢复连接再核对。

上传返回 202 只表示已排队，不能显示“已导入”。接口应把文件与最终运动或失败原因关联，重复重试不得重复导入。运动管理根据来源返回可用操作、可编辑字段和选项，保留手工/文件导入/Strava 模式差异。删除确认明确说明关联曲线、分段、原文件或图片的删除影响；不向移动端开放通用 `/admin/dispatchCommand`。

## 升级与兼容

- 保持正式包名 `io.stridehub.app`、原签名密钥和原称重数据库，递增版本号；支持覆盖安装。调试包继续独立。
- 保留服务器地址和用户名。旧网页登录 Cookie 不迁移成新凭据，首次升级提示重新登录；离线称重和已有本机历史仍然可用。
- 先提供兼容的后端移动接口，再发布依赖它的 APK；能力握手识别旧后端并给出明确升级说明。禁止退回 WebView。
- 新建缓存库不能触碰旧称重 UUID、原始测量、资料快照、CSV 去重记录、删除墓碑和队列绑定；升级测试必须覆盖这些内容。
- 移除生产代码中的 BrowserLayout、LoginScript、WebView 生命周期/导航和网页上传回调；保留并改造服务器地址验证、系统文件选择和现有称重业务测试。
- 不将本轮设计当作 NAS 部署或真实手机蓝牙验收；发布、部署和设备验证分别记录结果。

## 完成标准

1. 静态检查与 APK 检查确认不创建 WebView、不执行网页脚本、不使用 CookieManager 维持业务认证；核查直接和间接 UI 依赖，不允许隐藏的网页承载组件。
2. 对上述功能表逐项执行原生端到端验证，不存在空按钮、占位详情或跳网页完成业务。实际 API 数据显示成功才算完成，演示数据仅用于隔离测试。
3. 核验登录、过期、撤销、密码变更、非法凭据、子目录 URL、HTTP 明确选择、服务器/账号隔离。
4. 核验各栏目独立返回栈、旋转/进程重建、滚动与草稿恢复、系统返回、字体放大和 TalkBack。
5. 核验弱网/断网读缓存、恢复刷新、在线保存失败、409 冲突、重复点击和写入后读回；称重离线入库和联网去重同步。
6. 覆盖旧 APK 数据升级、历史 CSV 导入、已同步/待同步/冲突/删除记录、绑定切换和原账号队列恢复，不清理个人应用数据。
7. 用隔离后端与调试模拟器验证录入、计划反馈、运动导入与管理、任务状态和导出；不使用生产数据库作测试夹具。蓝牙收秤和真机交互另外实测，模拟器通过不能替代。
8. Android 构建、相关单元测试、lint、原生界面测试、后端鉴权/接口/任务/迁移测试通过；功能矩阵和实际设备验证范围随产物交付。

## 交付顺序与实施者可决定事项

后续实施计划按“后端移动会话及接口缺口 → 原生应用与数据层 → 四主栏目和详情 → 全部表单/导入/设置 → 统一称重 → 升级及端到端验收”组织。它们是开发阶段，不是允许中途以 WebView 混合版本作为最终交付。

实施者可以决定经过兼容性验证的依赖版本、包/文件拆分、网络与序列化库、图表绘制细节和可复用组件粒度。不得自行缩减零 WebView、已有功能覆盖、数据保存、账号隔离或离线称重要求。原生界面可逐页迭代视觉细节，不需要逐项征求技术许可。

参考：[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)、[离线优先数据层](https://developer.android.com/topic/architecture/data-layer/offline-first)。
